Problem

No safe way to see a flow run

Flows run automatically on a schedule. Builders needed to know a flow worked before it went live, and when it didn’t, which block failed and why.

Solution

A rehearsal, not a live run

A Test button opens a read-only test environment. It runs the flow on up to 10 real unread emails, gives a pass or fail log for each, and points the canvas at the block that failed.

Result

One log, one answer

Every tested email gets its own log. Open it and the canvas centres on the block that stopped it, with the API error beside it. Exit, and the results stay in the editor for the session.

About

Where Test fits

Simplifai’s Flow Builder lets teams chain AI skills into automated workflows that read and act on incoming email. Once a flow is published, it runs on its own.

This case study is about the step before that: the Test flow feature I worked on. It covers the button in the editor, the test environment, the logs for every tested email, and how Loop blocks changed what a log has to show.

Problem

A flow had to prove itself before it ran on its own

A published flow triggers on a schedule and acts on real email. If a block is misconfigured, or an account’s token has expired, the first sign is a failed run on a real customer message.

Builders needed a controlled way to run the flow by hand, on real input, and see the result block by block. That meant a test mode, and it also meant clear answers when something failed: which email, which block, what the API said.

Testing also had to avoid its own risks. A test must never collide with the live scheduler, or touch a flow someone else is editing.

Why solve it now

  • Trust. Customers handing email work to AI need to see it behave before they switch it on.
  • Safety. Test and scheduler must never run on the same flow at the same time.
  • Faster fixes. A failed test should lead straight to the block that needs attention.

Objective

Make testing feel like a controlled rehearsal: real emails, real blocks, a clear verdict for each email, and a short path from a failure back to the block that caused it.

What each person needed from Test

Running a test

As a user, I want to test the flow so I can check it works as expected. Test should open only when there is a source and one connected app.

Choosing what to test

As a user, I want the latest unread emails matching my source filters to be tested, so I test on realistic input.

Staying in control

As a user, I want to abort a running test, or retest on a new set of emails without leaving the test environment.

Reading the result

As a user, I want a log for each email, so I can see which passed and where the others failed.

Finding the cause

As a user, I want the canvas to show success and failure on each block, so I can see where an email stopped.

Coming back to it

As a user, I want the results in the editor after I exit, so I don’t have to remember what failed.

How a test run works

  1. Click TestEnabled only when the flow has a source and a connected app.
  2. Read the modalWhat will be tested, and which account to send emails to.
  3. Start testLatest unread emails matching the source filters are synced.
  4. Watch the statusView-only canvas, status header, test toolbar.
  5. Open the logsOne log per email. Retest, or exit back to the editor.

The run only ever touches unread emails that match the source, and marks only those as read. Anything that doesn’t match stays untouched in the inbox.

Core idea

Test in its own, read-only space

Because a test must never be confused with editing, or collide with a live run.

Test inside the editor

Fewer screens. But the canvas stays editable during a run, and a flow that is live could be changed and tested at once.

A separate test environment Chosen

The canvas becomes view-only, with its own toolbar and status. Nothing can be edited mid-run, and the editor stays clean.

The modal sets expectations first

Before anything runs, the modal says what a test does: the latest 10 unread emails that match the source are used, run data isn’t stored beyond the session, and it names the account to send test emails to.

What changed along the way

The first plan was to show errors inline inside the modal. That proved hard to do well, so I moved failures into a status header in the test environment. It was added during development, and it became the home for every failure message.

Every failure keeps Retest on, so the next step is always one click away.

Test logs

One email, one log, one place on the canvas

When a run completes, the Test Result panel opens on the right with one log per tested email. Log 1 is open by default, and only one log can be open at a time.

  • Failed log. The failed block gets an error mark and moves to the centre. Blocks before it show success. Blocks after it stay plain, because the email never reached them.
  • Passing log. The source moves to the centre and each block the email passed through shows success. Behind an And/Or, only the branch that was taken is marked.
  • Error details. The raw API response is shown and can be selected and copied, so it can go straight into a ticket.
  • Close the panel. The canvas returns to its plain state, and reopening starts from Log 1 again.
Loops · Sprint 20

When a block fails on the 3rd of 5 attachments

Once Loop blocks arrived, a single failed block was no longer enough information. The same block can pass on one attachment and fail on the next. The rule I held to: if one iteration fails, the whole log is a failed log.

Block fails outside a loop

Failure mark on the block, centred on the canvas, with its name, flow type and error details.

Block fails inside a loop

A card per failed iteration, showing the block, flow type, loop name and iteration number. Click a card and the canvas centres on that block and highlights the path to it.

Rules that keep testing safe

Learnings

Most of the design was in the edge cases

Put errors where there is room for them

Inline validation inside a small modal was hard to get right. A status header in the test environment gave every failure a clear home, and a Retest button beside it.

Let the canvas answer the question

Instead of making people hunt for the failing block, clicking a log centres it. Blocks the email never reached stay plain, so the picture matches what really happened.

Remove the ways a test can hurt a live flow

Disabling Test while a flow runs, one test per flow, and results visible only to the person who ran them were all small rules, but they are what makes testing safe to offer.

Left out for now: sources other than Gmail and Microsoft Graph, more than 10 emails per run, Primary and Generic flow labels for the Action failed feature (every failure currently reads as Primary), multi-user rules still being finalised, and keeping results beyond the session.
